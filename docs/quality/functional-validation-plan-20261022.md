# 灵爪收纳：功能质量与真机验证计划

日期：2026-10-22（Asia/Shanghai）。本轮保持 UI 设计，优先让识别、方案、生图、执行与保存可靠。本文是测试方案与现状核对，不是本轮全部通过报告；本文调研本身没有安装 App、发送照片、调用付费生图或创建线上服务，其他并行验证按下述范围分别记录。

当前最影响功能验收的三件事：

- **P1：真实生图未成功。** 本轮携带鉴权、绕过本机 HTTP 代理请求 `https://beeapi.dev/v1/models` 返回 200，配置模型可见；没有展示凭证。实际图片编辑请求第一次发生 HTTP/2 流中断（curl 92，约 26 秒），第二次改 HTTP/1.1 后等待 120 秒超时（curl 28），均未收到图片，随后停止付费重试。这尚不能确认供应商上游、线路或模型权限中的具体原因，也不能证明手机无代理可用。鉴权成功不等于生图成功。
- **P1：真实识别精度仍待评测。** 本轮已去掉拍照合并及云端解析器的静默数量上限，提示词改为分别列出可见实例，并将云端分类由旧 7 类补到现有 11 类；8 项定向回归通过。这些修复不代表 50 张真实图已达到 90% 或 95%。不能把类别组数当作已识别物品数。
- **P2：定位与轮廓要分开评价。** 云端候选缺少本地轮廓时使用矩形 raster；可显示遮罩不等于精确分割，不能借此宣称轮廓准确。

## 1. 建议采用的工作方式

把重复验证交给自动化，把真实拍摄、生成图可信度和用户理解留给真机观察。每个缺陷都留下输入照片、实际结果和版本，修复后用同一输入复测，再跑相关回归。这样用户只需提供新的真实场景，不必每改一行代码就从头整理一次桌子。

专业工具能承担的工作有明确边界：XCTest 可验证原生状态和存储；XCUIAutomation 可重复执行实际 UI 操作；测试附件可保存截图和文件；TestFlight 可收集测试者反馈、会话和崩溃信息；MetricKit 可提供设备上的性能与诊断报告。[1–4] 这些工具不会自动判断桌子有没有整理好，也不等于远程查看用户手机。

### 怎样看到手机上的真实效果

**现在无需服务器也能做：**

1. **本机优先用已经验证可用的 iPhone 镜像。** 本轮已在 Mac 的 iPhone 镜像中看到用户 iPhone 15 Pro Max 的真实主屏，具备从电脑点按/滚动实际 App 的入口；可由测试工具观察真实界面并执行已授权的 App 流程。需要拍摄真实桌面时仍由用户拿手机完成，不浏览无关相册或其他隐私内容。镜像/相机切换与手机解锁条件按系统实际状态处理，不能保证镜像期间直接实拍。
2. 用户只走一遍“拍照 → 确认识别 → 生成方案/效果图 → 完成一步 → 暂停/退出 → 恢复 → 完成照确认归档”。录屏保留出现问题前后各十几秒，记录具体时间。
3. 原始测试照片和保存的效果图通过系统分享、Files 或 AirDrop 传到本机任务目录。录屏用于看交互，原图/结果图用于评估识别和生图。只有截图，往往无法区分识别漏检、用户删改或图片下载失败。
4. 工程师把失败照片加入开发回归集、修复并生成新包；同一输入复测成功后，再让用户试新的真实场景。

需要保存录屏时，USB 连 Mac → QuickTime Player → 文件 → 新建影片录制 → 摄像头选择连接的 iPhone，是备用路径。[5] 此路径有官方说明，本轮未单独实际录制；不能把镜像可用当成已完成整条业务验收。

**现已提供小范围本机提取脚本：** [collect-device-feedback.py](../../scripts/collect-device-feedback.py)。默认设备已配置为当前连接手机，可通过 `--device` 覆盖；只读指定 App 容器内的两个诊断文件与 state，原始文件仅在临时目录处理，输出白名单字段。默认不提取照片；`--include-images` 才提取所选空间合法引用的 before/after 图，重新编码移除 EXIF。输出在已忽略的 `outputs/device-feedback-日期/`，不上传、不写手机、不读取钥匙串或配置导入文件。

```sh
python3 scripts/collect-device-feedback.py --self-test
python3 scripts/collect-device-feedback.py
python3 scripts/collect-device-feedback.py --session <空间UUID> --include-images
```

脚本已用假状态、假凭证、非法路径和带 EXIF 假图自检。2026-10-22 18:13 已从当前 iPhone 执行一次默认提取，成功导出脱敏生图诊断（`debug-import-succeeded`、`configured=true`、`hasConsent=false`）；设备尚无业务 state 或识别诊断文件，因此没有空间快照，尚未实测照片提取。结果在忽略目录 `outputs/device-feedback-20261022-181348/`。当前 state 没有独立扫描会话档案，`--session` 实际选择空间 UUID；默认按已有完成日期选空间，无日期时选最后空间，因此未必是最新拍摄。只导出当前候选和活动/最新完成方案的 ID、状态与关联物品，不导出自由文本计划、配置、URL、完整 mask 或其他空间。日志是最近全局事件，不能证明属于所选空间；生成图缓存没有可靠 session 关联，暂不提取。`photoPairRecorded` 只表明记录过前后照片，不证明真实整理质量。

当前真机交付已完成：iPhone 15 Pro Max 已安装并启动 1.0.0（2）；开发者信任在用户确认后完成，Key 已导入独立 Keychain，临时导入文件已删除。通过镜像核对空间、分类、项目、我的页面往返正常，未进行真实相机/整理全流程或新增付费生图；配置就绪不能替代 G1–G5 验收。详细结果见 [本轮功能验证记录](validation-results-20261022.md)。

**以后值得补的能力：完整会话反馈包。** 当前桥接已有 `scanDiagnostics`，含识别来源、本地/云端候选数量、模型名称及云端是否配置；仍缺完整会话 ID、阶段耗时与用户修正的连续事件。可通过开发调试入口或已有分享能力导出，不改变正式页面布局。理想的一次导出应包括：

```text

  manifest.json       # App/build、Git commit、网页资源 hash、iOS/机型、阶段时间、网络类型
```

默认本地保存和本地导出；包含房间照片的包，由用户明确选择后再分享。永不导出 Key、Authorization、完整账户配置、带临时签名的 URL、未经筛选的服务商响应体或无关项目数据。错误信息也可能回显凭证，采用字段白名单；用虚构测试 Key 验证脱敏。无需为本阶段上传到分析平台。

## 3. 五道验收门槛

阈值是项目建议/产品目标，不是 Apple 规定的上架标准。所有结果记录分母、样本来源、策略版本与运行环境；不足样本就写“待验证”。机器可读清单见 [acceptance-matrix-20261022.json](acceptance-matrix-20261022.json)。

### G1：主流程能完成，出错不丢数据

当前实际入口是 React + WKWebView + 原生桥接。保留原生方法测试和已有网页逻辑测试，再补少量跨桥接关键流程；纯网页 mock 通过不能替代原生持久化。

冻结以下六组场景，每组必须在最新包通过，无假成功、无重复归档、无旧结果污染：

1. 正常相机/相册 → 候选确认 → 本地方案 → 完成步骤 → 完成照预览 → 确认归档 → 重启后仍存在；预览与取消均不得提前归档。
2. 零识别/误识别 → 用户删除、改名或手动补录 → 仍可生成和完成；云端不可用不阻塞本地流程。
3. 暂停、后台、锁屏和强制退出后，进度与照片保持一致；WKWebView 前置指引阶段及原生步骤都要核对。
4. 重拍、返回、连续点两次、切到另一项目后，旧识别/生图请求迟到不得覆盖新会话；同一个动作最多落盘一次。
5. 相机首次拒绝、相册取消、无法联网、401、429、超时、图片下载失败均可退出或重试；生成失败时不以占位图声称成功。
6. 注入保存失败后不显示完成、不增加统计，原数据可恢复，重试后只保存一次。以测试存储/网络替身注入故障，避免真实付费请求制造错误。

真机至少覆盖首次相机授权、拒绝后恢复、拍照朝向、两次连续进入退出、一次前后台和一次重启。模拟器难以覆盖的相机/触摸/温升留到真机；长期与存储压力不要求用户每次重走。

### G2：识别准确，且能清楚说明漏了多少

沿用用户已确定的 **50 张独立真实照片**规模，建议分为 **35 张书桌、15 张茶几**；这个比例是项目建议，并非用户指定。此处是待采集/核验的留出目标集，不能把数量写成已经存在或已经通过。开发用合成图、网络例图和已反复调参的旧 6 图单独保留，不混入最终验证集。

- 先按家庭/空间分组，再分开发集和留出集；同一桌面换角度、裁剪或变亮不能跨组，避免看过答案。覆盖白天/夜间、反光、遮挡、近景/远景、10 件以下与较多物品；不要只挑本地模型认得的类别。
- 冻结前写清哪些物品算整理相关目标、如何处理重复实例、模糊/严重遮挡与忽略区域；逐物标类别/名称、框，必要时标轮廓。第二人复核争议；规则不得随结果变差而改。
- 对相关目标做完整标注，计算 `precision = TP / (TP + FP)`、`recall = TP / (TP + FN)`；一条预测只能匹配一个真值。名称同义词和匹配 IoU 门槛提前固定。旧稀疏 16 目标基线的未匹配候选不全是 FP，不能用其直接计算 precision。
- 用户此前要求总体效果 **90% 以上，争取 95%**，尚未把这个百分比分配给 precision 或 recall。为使目标可测，建议初始门槛采用 **precision ≥ 90%、recall ≥ 90% 两者同时满足**，再向 95% 改善；这是对目标的工程解释，不能写成用户已指定“90% precision / 95% recall”。分别报告书桌/茶几、错误类型和 50 张的置信区间，达标需真实运行；平均置信度或“有一个物体”都不能替代。若产品关心的是“95% 场景可用”，还须单独冻结场景可用定义。
- 本地离线、云端启用、降级回本地分别测，避免混出一个总分。评用户真正看到的列表，同时保留解析前、解析后、合并后的候选，回归确认密集场景不会因数量预算、实例合并或后续 UI 列表再次漏项。若发布 AR/轮廓能力，还要独立标注并测 mask IoU/Dice；框 IoU 不能替代轮廓指标。

冻结后根据失败样本修复，原冻结集可保留作回归，但其“首次盲测”地位已失去；后续另补真实新场景作确认集，不反复调到旧样本高分后称泛化已达标。

### G3：效果图是同一个空间，方案实际做得到

生图连通、返回 200、图片好看是不同结论。先用开发样本跑少量试验，提示词与模型确定后，再预先选定 **20 个未用于调参的真实场景**做效果验收；其中 5 个场景各加跑 2 次观察稳定性，共 30 次拟议请求。这里只规划，不自动消耗额度；预算和供应商权限未核时不执行批量生成。

两位评审并排看原图与生成图，独立核对：桌面/房间几何和视角保持；用户指定保留的物品仍存在；收纳位置可实现；没有凭空添加大件家具、窗户或删除重要物品；文字方案与效果图一致。是否“更整洁”另作主观项，不掩盖空间失真。

建议门槛：20 个首轮样本中至少 18 个通过全部硬条件，30 次中不出现严重空间改写/重要物品无理由消失；失败样本必须可重试或继续本地方案，不能假装原照片已变成现实。记录每次耗时、下载成功、取消和实际费用；“蜂窝/普通 Wi-Fi 关闭代理完整取回并保存”至少各有一次真机证据。一次可达不代表全国网络都可达。

### G4：数据与凭证在升级、失败和恢复后可信

新装、覆盖升级、系统终止、写盘失败后恢复都应保留正确项目/照片/步骤。重置仅在专用测试数据上操作，不清理用户手机真实内容。若用系统钥匙串保存 Key，确认不进入源码、App 资源、网页状态、反馈包或测试附件；生成图下载到本地后重启仍能显示，不能依赖短期外链。

本地模式不应向云端发送照片；启用云端前遵循实际同意状态，取消后不再发起新请求。计划中的导出包也需一份“假凭证与假照片”回归，确认脱敏且只导出选定会话。

### G5：真实使用者能独立完成

先邀请 5–8 位不熟悉项目的人做任务观察，不要提示点击位置。每人用自己的一个真实桌面完成“拍摄、修正、开始一项、暂停恢复、记录真实完成照”，记录能否独立完成、卡点、误识别修正数量、等待感受、是否信任生成图；不要求为测试搬动危险物品。

建议退出条件：至少 80% 无引导完成主任务，0 个未解决的崩溃/丢数据/隐私缺陷；所有导致中断的高优先级问题修复后复测。5–8 人是发现问题的小样本，不能由此宣传大规模成功率或稳定性。资格具备后使用 TestFlight 分发与收反馈；它无需自建分发服务器，但仍需 Apple 发行与 App Store Connect 条件，外部首个 build 可能需要 Beta App Review。[3]

## 4. 每个版本怎么测，才不把时间花在重复点屏幕

| 时机 | 执行者与内容 | 留下的证据 |
| --- | --- | --- |
| 每次相关代码改动 | 工程师跑受影响的原生/网页测试和固定失败照片；API 故障用替身 | 测试摘要、失败输入、修复前后对照 |
| 每个候选手机包 | 一次相机/相册主流程 + 暂停恢复 + 一次网络失败；保留原项目数据 | build/commit/网页 hash、短录屏、脱敏事件包 |
| 模型或提示词变更 | 全开发集回归、再按冻结协议运行留出评测 | 每图原始候选、真值、TP/FP/FN、分场景分布与成本 |
| 发布候选版 | 最新完整自动化、全部门槛、至少两种真实网络；可取得时测另一台最低支持机型 | 对应当前包的证据；不得沿用过期结果冒充 |

先记录真实手机的识别/生成/保存 p50、p95 耗时，再设适合目标设备的预算。故障测试要求在配置的请求超时后结束等待，取消后不污染状态；不为了漂亮均值删除超时和失败。MetricKit 的性能报告最多每天一次，不能当成实时录屏或每次请求日志；诊断报告与业务事件日志分别使用。[4]

修复顺序建议：① 生图真实连通与失败提示；② 识别漏检/错名及列表上限；③ 暂停、取消、晚到结果与落盘恢复；④ 效果图保真和方案可执行；⑤ 真机等待时间与耗电。发布还须另过发行资格、工具链、模型许可、隐私/支持页等既有上架门槛，功能通过不能替代这些条件。
